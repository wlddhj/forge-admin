# 条件节点使用指南

> 适用模块: `forge-module-workflow`
> 适用人员: 流程设计者 / 后端开发
> 关联文档: [工作流使用说明](01.workflow-usage.md) §6 条件节点(路由) / [触发器 Bean 开发指南](03.trigger-bean-guide.md) §3.4

---

## 1. 概述

FlowLong 引擎支持两种"条件"相关节点:

| 类型 | 名称 | 实际作用 |
|---|---|---|
| `type=3` | `conditionNode`(条件审批) | **作为 type=4 的子节点使用**,或独立作为"条件审批"节点(行为近似 type=1) |
| `type=4` | `conditionBranch`(条件分支) | 排他网关,按条件路由到不同 childNode |

> ⚠️ **关键澄清**(纠正常见误解):
> **`type=3` 单独使用时,其配置的 conditionList 不会影响流程分支**。`TaskServiceImpl.java:1244-1250` 的处理逻辑与 `type=1` approval **完全相同**(直接生成 task)。要让条件判断真正起作用,必须把 `type=3` 作为 `type=4` 的**子节点**使用。

---

## 2. type=3 条件审批(条件列表什么时候生效)

### 2.1 作为 type=4 子节点 — 条件生效

```
[type=4 条件分支]
  ├─ [type=3 子节点 1, conditionList: [riskLevel=='A'], childNode: 法务审批]
  ├─ [type=3 子节点 2, conditionList: [riskLevel=='B'], childNode: 部门负责人]
  └─ [type=3 子节点 3, conditionList: [],              childNode: 结束]   ← 兜底
```

type=3 子节点的 `conditionList` 会被 `SimpleConditionNodeHandler.getConditionNode()` 读取,按 priorityLevel 升序逐个求值,第一个 true 胜出。

### 2.2 作为独立节点 — 条件**不**生效

```
[type=3 条件审批]  ← 独立节点
  │  (不嵌入 type=4)
  │
  childNode
```

`TaskServiceImpl.java:1244-1250`:

```java
} else if (TaskType.conditionNode.eq(nodeType)) {
    FlwTask singleFlwTask = flwTask.cloneTask(flowLongIdGenerator, null);
    PerformType performType = PerformType.get(nodeModel.getExamineMode());
    flwTasks.addAll(this.saveTask(singleFlwTask, performType, taskActors, execution, nodeModel));
}
```

**关键发现**: 这段代码**与 type=1 approval 完全一样** — 克隆 task、读取 performType、保存 task。**没有读取 conditionList,也没有任何条件判断**。

也就是说,如果你把 type=3 拖出来单独用,前端配置的 conditionList **只是元数据,不影响流程**。如果想"条件判断后决定是否生成任务",正确做法是:
- ❌ 单独一个 type=3(条件列表不生效)
- ✅ type=4 + 多个 type=3 子节点(每个子节点代表一个"条件+审批人"组合)

### 2.3 何时考虑用独立 type=3

实际场景中独立 type=3 几乎不用,因为它的行为 ≈ type=1。**唯一合理场景**:为了让审计/流程图显示更清晰(type=3 表示"带条件上下文的审批")。

## 3. type=4 条件分支 — 真正的"条件路由"

### 3.1 处理流程

```
NodeModel.execute()                            (NodeModel.java:315)
  │
  ├─ if TaskType.conditionBranch.eq(this.type):
  │     flowLongContext.getFlowConditionHandler()
  │         .getConditionNode(flowLongContext, execution, this)
  │         .ifPresent(t -> this.executeConditionNode(flowLongContext, execution, t));
  │     return true;
  │
  └─ ...
```

调用链:

```
SimpleConditionNodeHandler.getConditionNode(nodeModel)
  │
  ├─ 1. 检查 FlowDataTransfer.processSpecifyConditionNodeKey
  │     (审批人显式指定了分支,跳过条件求值)
  │
  ├─ 2. AI 智能路由决策(若 nodeModel.getCallAi() != null)
  │     → FlowAiHandler.decideRoute(...) 选 AI 决定的 NodeKey
  │
  └─ 3. SpEL 条件求值(默认路径)
        matchConditionNode() 按 priorityLevel 升序遍历:
          条件1 eval → true ✓ 命中 → 返回
          条件2 eval → false
          条件3 eval → false
        → 没匹配 → defaultConditionNode(conditionList 为空的)
                     找不到 → 抛 "Not found executable ConditionNode"
```

### 3.2 条件求值机制(SpEL 自动拼接)

**核心源码** `FlowLongExpression.java:45-62`:

```java
default boolean eval(List<List<NodeExpression>> conditionList, Supplier<Map<String, Object>> argsSupplier, Function<String, Boolean> evalFunc) {
    if (ObjectUtils.isEmpty(conditionList)) {
        return false;
    }
    Map<String, Object> args = argsSupplier.get();
    
    // 关键:任一变量缺失 → 整个条件判 false
    for (List<NodeExpression> nodeExpressions : conditionList) {
        if (nodeExpressions.stream().anyMatch(t -> !args.containsKey(t.getField()))) {
            return false;
        }
    }
    
    // 自动拼 SpEL 表达式:组内 AND,组间 OR
    String expr = conditionList.stream()
        .map(cl -> cl.stream().map(t -> exprOfArgs(t, args))
            .collect(Collectors.joining(" && ")))
        .collect(Collectors.joining(" || "));
    return evalFunc.apply(expr);
}
```

**`exprOfArgs` 单条条件转 SpEL** (`FlowLongExpression.java:64-71`):

```java
default String exprOfArgs(NodeExpression e, Map<String, Object> args) {
    Object fieldValue = args.get(e.getField());
    if (fieldValue instanceof String) {
        return "#" + e.getField() + " " + e.getOperator() + " '" + e.getValue() + "'";
    }
    return "#" + e.getField() + " " + e.getOperator() + " " + e.getValue();
}
```

**自动生成示例**(`conditionList = [ [{riskLevel == 'A'}], [{urgent == true}] ]`):

```
#riskLevel == 'A' || #urgent == true
```

注意: 流程变量自动加 `#` 前缀,作为 SpEL 变量。

### 3.3 嵌套结构含义

`conditionList: List<List<NodeExpression>>` 是**两层嵌套**:

```
conditionList = [
  [条件A, 条件B],   ← 条件组1(组内 AND)
  [条件C],          ← 条件组2(组内 AND)
]
```

求值语义:
- 条件组1: `A && B`
- 条件组2: `C`
- 整体: `(A && B) || C`

## 4. 触发条件在流程中的使用时机

### 4.1 时序图(以合同分级审批为例)

```
[t0] 用户提交合同,amount=2000000
      流程实例创建,args = { amount: 2000000 }

[t1] 流程进入「触发器」节点
      TaskTriggerHandler.execute()
        → Bean computeRisk(2000000) 返回 'A'
        → setVar(execution, "riskLevel", "A")
        → args 现在 = { amount: 2000000, riskLevel: "A" }

[t2] 流程进入「条件分支」节点(type=4)  ← 触发条件在这里被读取
      SimpleConditionNodeHandler.getConditionNode()
        ① 查 FlowDataTransfer.processSpecifyConditionNodeKey(未设置,跳过)
        ② AI 路由决策(未启用,跳过)
        ③ matchConditionNode():
           按 priorityLevel 升序遍历:
             条件1 (priority=1, riskLevel=='A'): eval → true ✓ 命中
             条件2 (priority=2, riskLevel=='B'): 已短路,不再求值
           返回 条件1
      → executeConditionNode(条件1)
        → 条件1.childNode (法务审批) execute()

[t3] 法务 task 入库,流程停在法务审批节点
```

**关键点**:`riskLevel` 必须**在 t2 之前**(即 t1 触发器阶段)**已经写入** `execution.getArgs()`。

### 4.2 条件变量准备的"先后"约束

| 准备时机 | 写入方式 | 典型场景 |
|---|---|---|
| 启动时传入 | 发起 API `variables` 参数 | 用户填表提交 |
| 触发器节点写 | `T(SpelUtil).setVar(...)` 或 Bean `setVar(...)` | 业务计算结果 |
| 审批节点写 | 审批意见 / 附加数据 | 审批人提交意见时 |
| 外部系统写 | `Execution.setArg(...)` | 系统集成 |

**反例**: 想"用户提交 → 条件分支读 amount → 走不同路径" — 要求 `amount` 在**发起时**就传入 `variables`,否则条件求值时拿不到。

## 5. 变量缺失时的行为

**关键源码** `FlowLongExpression.java:53`:

```java
if (nodeExpressions.stream().anyMatch(t -> !args.containsKey(t.getField()))) {
    return false;  // 任一变量缺失 → 整个 conditionList 判 false
}
```

**行为**:
- 条件1: `riskLevel == 'A'` 求值时,args 里没有 `riskLevel` → **该条件判 false**
- 条件2: `riskLevel == 'B'` 同样判 false
- 条件3: `riskLevel == 'C'` 同样判 false
- 都没匹配 → 走 `defaultConditionNode()`(找 conditionList 为空的)
- 还找不到 → **抛 "Not found executable ConditionNode"**,实例卡住

**排查信号**: 后端日志搜 `Match condition`,能看到实际命中哪条条件。

## 6. 兜底机制(default 分支)

**源码** `SimpleConditionNodeHandler.java:120-122`:

```java
public Optional<ConditionNode> defaultConditionNode(List<ConditionNode> conditionNodes) {
    return conditionNodes.stream()
        .filter(t -> ObjectUtils.isEmpty(t.getConditionList()))  // 找"无条件"分支
        .findFirst();
}
```

**典型用法**:`type=4` 设计时,把**最后一个 conditionNode 的 conditionList 留空**(无条件),作为"以上都不匹配时的兜底":

```javascript
// addNode.vue 默认行为(已实现)
conditionNodes: [
  { nodeName: '条件1', priorityLevel: 1, conditionList: [...], childNode: ... },
  { nodeName: '条件2', priorityLevel: 2, conditionList: [...], childNode: ... },
  { nodeName: '条件3', priorityLevel: 3, conditionList: [],  // ← 兜底:无条件
    childNode: <结束节点或某个默认路径> }
]
```

## 7. 实战注意事项

### 7.1 不要让 conditionList 引用"瞬时"变量

如果触发器节点执行失败被跳过,变量可能没设置。**两种解决方案**:

1. **用兜底分支** — conditionList 为空的 conditionNode 捕获所有不匹配的情况
2. **触发器配置 `continueOnError=true`** — 即使触发失败也继续流转(走兜底)

### 7.2 SpEL 安全

`FlowLongExpression` 拼字符串后传给 SpEL 求值,**args 中的 key 会被拼到 SpEL 上下文**(`#riskLevel`)。

如果 args 来自不可信源(外部 API 提交),理论上有 SpEL 注入风险。

**生产建议**:
- 只读 `execution.getArgs()` 而不让外部塞任意 key
- 限制 args 的 key 在白名单内

### 7.3 跨分支的变量访问

条件判断只看 type=4 **自己的** conditionNodes 里的 conditionList;不会跨分支读。各分支的 conditionList 是**独立声明的**,但引用的字段都从同一个 args 读。

### 7.4 SpEL 求值失败的处理

如果 `FlowLongExpression.eval` 抛异常(如类型不匹配、SpEL 语法错):
- `SimpleConditionNodeHandler.matchConditionNode` 没 try-catch,异常向上冒泡
- 引擎会把节点当失败处理,实例卡住

**典型原因**:
- conditionList 里 `value` 类型与 args 中 `field` 的实际类型不一致(如 field 是 Long,value 写了 String "abc")
- 用了 args 中不存在的字段

**排查**: 后端日志看 `Match condition: ...` 之前的异常堆栈。

### 7.5 优先级 vs 数组顺序

`conditionNodes` 的**匹配顺序按 `priorityLevel` 升序**,不是按数组下标。

```javascript
// ❌ 错误理解:按数组下标匹配
conditionNodes: [
  { priorityLevel: 5, ... },  // 这个不会"先"被检查
  { priorityLevel: 1, ... },  // 这个会"先"被检查
]

// ✅ 正确:按 priorityLevel 升序
```

`SimpleConditionNodeHandler.java:103-106`:

```java
return conditionNodes.stream()
    .sorted(Comparator.comparing(ConditionNode::getPriorityLevel))  // ← 按 priorityLevel 排序
    .filter(t -> flowLongExpression.eval(t.getConditionList(), args))
    .findFirst();
```

## 8. 完整示例:触发器 + 条件分支组合

### 8.1 流程图

```
[发起人] ──→ [触发器:分级] ──→ [条件分支] ──┬─ A级 → [法务] → [财务] → [CEO] ──→ [结束]
                                          ├─ B级 → [部门负责人] → [法务] ──→ [结束]
                                          ├─ C级 → [部门负责人] ──→ [结束]
                                          └─ 其他  ──→ [结束]  ← 兜底
```

### 8.2 触发器 Bean

```java
@Component
@FlowLongTrigger(name = "合同风险评估", description = "根据 amount 写 riskLevel")
public class ContractRiskTrigger extends AbstractFlowLongTrigger {
    @Override
    public boolean execute(Execution execution, NodeModel nodeModel, Map<String, Object> ctx) {
        Long amount = requireArgAs(ctx, "amount", Long.class);
        String riskLevel = amount >= 1_000_000 ? "A" : amount >= 100_000 ? "B" : "C";
        setVar(execution, "riskLevel", riskLevel);  // ← 关键:写流程变量
        return true;
    }
}
```

### 8.3 条件分支(条件子节点配置)

| 子节点 | priorityLevel | conditionList | childNode |
|---|---|---|---|
| 条件1 | 1 | `[[{field:riskLevel, op:==, value:A}]]` | 法务审批 → 财务审批 → CEO 审批 |
| 条件2 | 2 | `[[{field:riskLevel, op:==, value:B}]]` | 部门负责人 → 法务审批 |
| 条件3 | 3 | `[[{field:riskLevel, op:==, value:C}]]` | 部门负责人 |
| 兜底 | 4 | `[]`(空 = 无条件) | 结束 |

### 8.4 执行流程

用户提交 amount=2000000:

```
[t1 触发器] riskLevel = 'A', args = { amount: 2000000, riskLevel: 'A' }
[t2 条件分支] 遍历:
  条件1: riskLevel == 'A' → eval → true ✓ 命中
  → 法务审批 → 财务审批 → CEO 审批
```

用户提交 amount=50000(没触发器处理也走兜底):

```
[t1 触发器] riskLevel = 'C'
[t2 条件分支] 遍历:
  条件1: riskLevel == 'A' → false
  条件2: riskLevel == 'B' → false
  条件3: riskLevel == 'C' → true ✓ 命中
  → 部门负责人
```

用户提交 amount=1000(超小金额,riskLevel = 'C' 仍命中)但假设业务规则修改,所有 condition 都不匹配:

```
[t2 条件分支] 遍历:
  条件1, 2, 3 都不匹配
  → 兜底(条件4, conditionList=[])
  → 结束节点
```

### 8.5 关键提醒

> ⚠️ **不要试图用单个 type=3 节点配 conditionList 实现条件路由**。type=3 单独用时,引擎不读 conditionList(与 type=1 行为一致)。正确做法是 type=4 + 多个 type=3 子节点。

## 9. 排查速查

| 现象 | 原因 | 排查 |
|---|---|---|
| 条件节点走了不该走的分支 | 变量在求值时未写入 | 1. 看触发器节点日志,确认 setVar 成功<br>2. 查 `flw_instance.variable` 字段,确认 args 实际内容 |
| 条件节点卡住,日志 "Not found executable ConditionNode" | 所有条件不匹配且无兜底 | 加一个 conditionList=[] 的 conditionNode |
| 条件判断返回 false(不抛错) | 引用了 args 中不存在的字段 | `FlowLongExpression.eval` 行为:任一字段缺失 → false |
| SpEL 求值抛异常,实例卡住 | value 类型与 field 不匹配 | 查后端日志异常堆栈,确认是哪个 conditionNode 出错 |
| 条件分支顺序不符合预期 | 按 priorityLevel 而非数组下标匹配 | 检查所有 conditionNode 的 priorityLevel 值 |
