# 业务回调指南(Webhook 事件订阅)

> 适用模块: `forge-module-workflow`
> 适用人员: 外部系统集成方 / 流程管理员 / 后端开发
> 关联文档: [工作流使用说明](01.workflow-usage.md) §11 事件订阅选型 / §12 权限码
> 交付版本: 2026-10-27(commit 90270f0),建表 SQL `sql/upgrade-20261027-callback.sql`(dev 库须手工执行)

## 1. 定位一句话

外部系统通过 HTTP webhook 感知流程事件(任务创建/任务办结/实例终态),全程在「流程管理 → 业务回调」页面配置,无需写代码接入 forge-admin 进程,保存即生效。

与进程内订阅的分工: 进程内扩展用 Spring 事件(`WorkflowTaskEvent` / `WorkflowInstanceEvent`)或触发器 Bean([03.trigger-bean-guide.md](03.trigger-bean-guide.md));跨系统通知用本回调。

## 2. 快速开始(流程管理员视角)

路径: **流程管理 → 业务回调 → 新增**

| 字段 | 必填 | 说明 |
|---|---|---|
| 回调名称 | ✓ | 标识,如「OA 合同系统回调」 |
| 回调地址 | ✓ | 接收方 http/https POST 端点 |
| 订阅事件 | ✓ | 多选: 任务创建 / 任务办结 / 实例终态 |
| 流程过滤 |  | 填流程 `processKey` 只订阅该流程,留空=全部流程 |
| 签名密钥 |  | HMAC-SHA256 密钥;留空不签名(生产强烈建议配置) |
| 携带流程变量 |  | 仅对实例终态事件生效,终态时附带流程变量(注意敏感数据) |
| 超时(毫秒) |  | HTTP 连接+读取超时,默认 5000 |
| 状态 | ✓ | 启用/停用 |

## 3. 事件类型与引擎映射

契约事件是**稳定对外契约**,与引擎内部枚举解耦(引擎升级不改变对外事件):

| 契约事件 | 触发时机 | 引擎事件映射 |
|---|---|---|
| `taskCreated` | 到达节点产生待办 | TaskEventType.create / recreate |
| `taskCompleted` | 任务办结 | TaskEventType.complete |
| `instanceFinished` | 实例终态 | forceComplete / rejectComplete / revokeComplete / timeoutComplete / autoComplete / autoReject / end |

注意: 委派/转办/加签/催办等**中间操作不产生回调**,只有上述三类;`recreate`(驳回重提等场景重建任务)会再次投递 `taskCreated`,接收方需幂等(§7)。

---

## 4. 投递机制

- **触发时机**: 流程主事务提交后(AFTER_COMMIT)在 `workflowExecutor` 异步线程投递——回调失败绝不影响审批主链路,内部异常全部吞掉
- **请求**: HTTP POST,`Content-Type: application/json`
- **成功判定**: 接收方返回 HTTP 2xx
- **重试**: 失败后按 0s / 2s / 10s 共 **3 次尝试**(异步线程内 sleep,不占 web 线程)
- **审计**: 每次投递取终态落 `wf_callback_record`(状态 SUCCESS/FAILED、HTTP 状态码、响应体截断 2000 字符、重试次数、错误信息)

## 5. 签名与验签(接收方必读)

配置了签名密钥的回调,每次请求携带:

| 请求头 | 值 |
|---|---|
| `X-Forge-Timestamp` | 毫秒时间戳 |
| `X-Forge-Signature` | `Base64( HmacSHA256( secret, timestamp + "." + rawBody ) )` |

**验签要点**:

1. 必须用**原始报文体字节**(raw body)复算——先反序列化再重新序列化会因字段顺序/空白差异验签失败
2. 推荐校验 `X-Forge-Timestamp` 与当前时间差(如 ±5 分钟)防重放
3. 比较签名用常量时间算法(防时序侧信道)

**Java 最小验签示例**(与服务端 `CallbackSigner` 对齐):

```java
public boolean verify(String secret, String timestamp, String rawBody, String signature) {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    byte[] raw = mac.doFinal((timestamp + "." + rawBody).getBytes(StandardCharsets.UTF_8));
    String expected = Base64.getEncoder().encodeToString(raw);
    return MessageDigest.isEqual(
            expected.getBytes(StandardCharsets.UTF_8),
            signature.getBytes(StandardCharsets.UTF_8));
}
```

## 7. 接收方实现建议

- **幂等**: 重试与 `recreate` 都可能造成重复投递,建议按业务语义(如 `instanceId`+`taskId`+`eventType`)做幂等去重
- **快速响应**: 先落库/入队再返回 2xx,重逻辑异步处理——处理慢会触发超时重试,同一事件反复到达
- **敏感数据**: `variables` 原样携带流程变量,含敏感字段时谨慎开启,回调地址建议使用 https
- **排查入口**: 回调列表「投递记录」抽屉,或直查 `wf_callback_record`(§8)

## 8. 数据表、接口与权限

| 对象 | 说明 |
|---|---|
| `wf_business_callback` | 回调配置表,按租户隔离(`tenant_id`) |
| `wf_callback_record` | 投递记录表,失败排查主入口 |
| `GET /admin-api/workflow/callback/{id}/records` | 投递记录分页查询(可按 status 过滤) |
| `workflow:callback:list / query / add / edit / delete` | 菜单权限码 |

**排查 SQL**:

```sql
-- 最近 20 条投递
SELECT id, callback_name, event_type, instance_id, status, http_status, retry_count, error_msg, create_time
FROM wf_callback_record ORDER BY id DESC LIMIT 20;

-- 按状态统计
SELECT status, COUNT(*) FROM wf_callback_record GROUP BY status;
```

## 9. FAQ

**Q1: 配置了为什么收不到?**

A: 依次核对——状态=启用;订阅事件与实际事件匹配(§3 映射);「流程过滤」processKey 是否写对(留空才是全部流程);查 `wf_callback_record` 是否 FAILED(接收方返回非 2xx、网络不通、超时)。

**Q2: 回调会影响审批流程吗?**

A: 不会。事务提交后异步投递 + 异常全部吞掉,回调挂了流程照常流转,代价只是投递记录标 FAILED。

**Q3: 同一事件会投给多个回调吗?**

A: 会。所有「启用 且 订阅了该事件 且(流程过滤为空或等于该流程 processKey)」的回调各自独立投递、独立重试、独立记审计。

**Q4: 多租户下如何隔离?**

A: 回调配置按租户隔离,各租户在「业务回调」页维护自己的配置;表带 `tenant_id`,查询自动过滤。
