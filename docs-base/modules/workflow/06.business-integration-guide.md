## 1. 定位一句话

本文回答一个问题: **"我有一个请假单/报销单/合同,怎么让它接入审批流并随流程状态联动?"** —— 覆盖从流程准备、发起对接、事件订阅、状态回写到联动操作的完整步骤。

## 2. 两种接入形态怎么选

| | 形态 A: 平台内 Java 模块 | 形态 B: 外部系统 |
|---|---|---|
| 运行位置 | forge-server 同 JVM(新增 forge-module-xxx-biz) | 独立系统,走 HTTP |
| 发起方式 | 注入 `WfProcessInstanceService` | `POST /workflow/instance/start` |
| 事件感知 | Spring 事件(`WorkflowTaskEvent`/`WorkflowInstanceEvent`) | Webhook 回调(HMAC 验签,自动重试) |
| 认证 | 无需(用户上下文来自请求线程) | 平台登录令牌 `Authorization: Bearer <token>` |
| 事务/一致性 | 可选 AFTER_COMMIT 语义,与平台同库 | 跨网络,靠回调重试 + 业务幂等 |
| 适用 | 平台内新业务模块(推荐) | 已有独立系统、跨语言集成 |

两种形态可混用: 平台内模块用 A,同时给第三方开 B 的回调订阅。下文每种能力分别给出 A/B 两版步骤。

## 3. 对接前置: 流程准备(管理员/流程设计者侧)

按 [01.workflow-usage.md §4 完整配置流程](01.workflow-usage.md) 完成: 建分类(可选) → 建表单(可选) → 设计模型 → **部署**。业务开发对接前需要向流程管理员要到两样东西:

1. **processDefinitionId** —— 部署后「审批流程」列表里的流程定义 ID(注意不是模型 ID)。**推荐不要硬编码 ID**: 门面提供 `WfProcessDefinitionService.getLatestDefinitionIdByKey(processKey)`,按模型 Key 取最新部署版本,重新部署后自动跟随(实例模块 `forge.demo.project-process-key` 即此姿势);
2. **表单字段与流程变量的约定** —— 分支条件、候选人表达式里引用了哪些变量名(见 [02.condition-node-guide.md](02.condition-node-guide.md)),发起时必须原样传齐,变量缺失会走兜底分支。

建模时与业务相关的三个关键配置:

| 配置 | 位置 | 对业务的意义 |
|---|---|---|
| 分支条件引用的变量 | 排他/包容网关 | 发起时 `variables` 必须包含这些 key |
| 候选人策略 | 审批节点 | 是否需要 `startUserSelectActors`(发起人自选审批人)取决于此处配置,见 [01.workflow-usage.md §5](01.workflow-usage.md) |
| 触发器节点(可选) | 独立节点 | 流程走到该节点时回调业务 Bean,见 [03.trigger-bean-guide.md](03.trigger-bean-guide.md) |

## 4. 业务数据模型设计(第一步,最容易被忽略)

接入前先在业务侧定好三件事,返工成本最高的就是这一步:

**① businessKey 规范。** 发起时传入,是业务单据与流程实例的唯一关联键。建议 `{业务类型}:{单据ID}`(如 `leave:10086`),**唯一性由业务侧保证** —— 引擎允许同一 businessKey 存在多个实例(重发场景),查回的是列表。

**② 业务表加两个字段:**

```sql
ALTER TABLE biz_leave ADD COLUMN process_instance_id BIGINT NULL COMMENT '流程实例ID(发起后回写)';
ALTER TABLE biz_leave ADD COLUMN approve_status VARCHAR(20) NOT NULL DEFAULT 'DRAFT'
    COMMENT '审批状态 DRAFT审批中APPROVED/REJECTED/CANCELED(仅由事件回写,禁止手工更新)';
```

**③ 状态机收敛。** 业务状态只由两处驱动: 发起动作(→审批中)和实例终态事件(→通过/驳回/撤销)。审批中的中间流转(加签/转办/驳回重提)不改业务状态,只做展示。

## 5. 发起流程

### 5.1 形态 A: Java 注入服务

业务模块 pom 增加依赖(版本由 forge-dependencies 统一管理,不写 version):

```xml
<dependency>
    <groupId>com.forge</groupId>
    <artifactId>forge-module-workflow-biz</artifactId>
</dependency>
```

发起代码:

```java
@RequiredArgsConstructor
@Service
public class LeaveWorkflowService {

    private final WfProcessInstanceService instanceService;

    @Transactional(rollbackFor = Exception.class)
    public void submitLeave(Long leaveId) {
        BizLeave leave = leaveMapper.selectById(leaveId);
        // 校验: 同一单据不允许并发发起多个在途实例
        List<ProcessInstanceResponse> actives = instanceService
                .getInstancesByBusinessKey("leave:" + leaveId).stream()
                .filter(i -> i.getEndTime() == null)
                .toList();
        if (!actives.isEmpty()) {
            throw new BusinessException(400, "该单据已有在途审批流程");
        }

        ProcessStartRequest request = new ProcessStartRequest();
        request.setProcessDefinitionId(defId);             // 推荐 getLatestDefinitionIdByKey(key) 解析,见 §3
        request.setBusinessKey("leave:" + leaveId);        // ① 单据关联键
        Map<String, Object> vars = new HashMap<>();
        vars.put("days", leave.getDays());                 // ② 分支条件/候选人表达式引用的变量
        vars.put("amount", leave.getAmount());
        request.setVariables(vars);
        request.setUrgent(2);                              // ③ 紧急程度 0-3,可选
        instanceService.startProcess(request);
    }
}
```

**两条硬约束:**

- `startProcess` 内部取 `SecurityUtils.getCurrentUserId()`,**必须在认证请求线程内调用**(正常 Controller/Service 链路即可)。定时任务、MQ 消费等无用户上下文的线程里不能直接调;系统级发起走「触发器 + HTTP 带用户令牌」或改造为独立入口。
- 租户上下文随 `FlowCreatorFactory` 传导(见 §8),业务代码**禁止绕过服务直接 new `FlowCreator` 或调 `FlowLongEngine`**。

**发起后回写 instanceId:** `startProcess` 返回 `void`,发起成功后用 businessKey 查回实例 ID:

```java
List<ProcessInstanceResponse> instances = instanceService.getInstancesByBusinessKey("leave:" + leaveId);
ProcessInstanceResponse latest = instances.get(0);   // 列表按需取在途实例(endTime == null)
leave.setProcessInstanceId(Long.parseLong(latest.getId()));
```

> 请求线程内同步查即可: startProcess 返回时首任务已创建落库。同一事务里若本模块回写与发起同库,注意 startProcess 内部引擎事务与业务事务的边界,回写失败会导致"有流程无关联"—— 建议回写放在发起之后同事务,或依赖事件补偿。

### 5.2 形态 B: HTTP

```bash
curl -X POST 'http://<host>:8180/admin-api/workflow/instance/start' \
  -H 'Authorization: Bearer <平台登录令牌>' \
  -H 'Content-Type: application/json' \
  -d '{
    "processDefinitionId": "1234567890",
    "businessKey": "leave:10086",
    "variables": { "days": 5, "amount": 3000 },
    "urgent": 0
  }'
```

`ProcessStartRequest` 字段:

| 字段 | 类型 | 说明 |
|---|---|---|
| processDefinitionId | String | 必填,流程定义 ID |
| businessKey | String | 业务关联键,建议 `{业务类型}:{单据ID}` |
| variables | Map | 流程变量,须覆盖分支条件引用的全部 key |
| comment | String | 提交意见 |
| startUserSelectActors | Map<String, String[]> | 发起人自选审批人,key 为节点 taskDefKey(建模配置了才需要) |
| priority | Integer | 0-1,默认 0 |
| urgent | Integer | 紧急程度 0 常规/1 重要不紧急/2 紧急不重要/3 紧急且重要,默认 0 |

发起成功同样返回 `void`;外部系统通过 `GET /workflow/instance/by-business-key?businessKey=leave:10086` 查回实例列表(含 `id`、`endTime` 判在途)。

## 6. 事件订阅与状态回写

业务单据状态随流程推进联动,是接入的核心闭环。三种方式按场景选:

| 方式 | 形态 | 适用 |
|---|---|---|
| Spring 事件监听(§6.1) | A | 平台内模块回写业务状态(推荐) |
| Webhook 回调(§6.2) | B | 外部系统感知事件 |
| 触发器节点(§6.3) | A | 在流程的**特定节点**执行业务逻辑(扣库存、发预占),而非状态回写 |

### 6.1 形态 A: 监听 Spring 事件

引擎每次任务/实例状态变化都会发布 Spring 事件,业务模块加一个 Handler 即可:

- `WorkflowTaskEvent` —— 任务事件,携带 `eventType`(`TaskEventType`: create/complete/resume/reject/transfer/delegate…)、`taskId`、`taskName`、`instanceId`、`taskActors`、`nodeModel`
- `WorkflowInstanceEvent` —— 实例事件,携带 `eventType`(`InstanceEventType`: start/suspend/end 正常结束/timeoutComplete 超时办结/autoComplete/autoReject/rejectComplete/revokeComplete)、`instanceId`、`processId`、**`businessKey`**、`instance`(FlwHisInstance,含 `instanceState` 终态细分)

状态回写示例(终态以实例事件为准):

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class LeaveWorkflowEventHandler {

    private final BizLeaveMapper leaveMapper;

    @Async
    @EventListener
    public void onInstanceEvent(WorkflowInstanceEvent event) {
        String businessKey = event.getBusinessKey();
        if (businessKey == null || !businessKey.startsWith("leave:")) {
            return; // 不是本业务的流程,快速跳过
        }
        Long leaveId = Long.parseLong(businessKey.substring("leave:".length()));
        switch (event.getEventType()) {
            // end=正常走完; timeoutComplete=超时自动办结(超时策略语义,归通过,视业务可细分)
            case end, autoComplete, timeoutComplete -> updateStatus(leaveId, "APPROVED", event);
            // rejectComplete 有两义,按 instanceState 细分: 5=terminate 发起人取消, 2=reject 审批驳回
            case rejectComplete -> updateStatus(leaveId,
                    Integer.valueOf(5).equals(event.getInstance().getInstanceState()) ? "CANCELED" : "REJECTED", event);
            case autoReject -> updateStatus(leaveId, "REJECTED", event);
            case revokeComplete -> updateStatus(leaveId, "CANCELED", event);
            default -> { /* start/suspend 等中间态不回写 */ }
        }
    }

    private void updateStatus(Long leaveId, String status, WorkflowInstanceEvent event) {
        BizLeave update = new BizLeave();
        update.setId(leaveId);
        update.setApproveStatus(status);
        update.setProcessInstanceId(event.getInstanceId());
        leaveMapper.updateById(update);   // 幂等: 终态重复事件写同值,天然无害
    }
}
```

三条纪律:

1. **先过滤再处理。** 平台所有流程的事件都会广播到你的 Handler,开头按 businessKey 前缀(或 processId)过滤。
2. **事务边界。** 普通 `@EventListener` 在发布者事务**内**同步执行(若未 @Async),业务回写失败会连带流程操作失败。要"流程提交成功后再回写",参照 `BusinessCallbackEventListener` 用 `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)`。
3. **幂等。** 事件可能重复投递(如 AFTER_COMMIT + 引擎重试),终态回写按"写同值无害"设计,非终态累计类操作(如通知计数)须按 instanceId+eventType 去重。

平台内现有消费者可参考: `AuditLogEventHandler`(审计落库)、`WfAutoCopyEventHandler`(自动抄送)、`BusinessCallbackEventListener`(回调投递)。

### 6.2 形态 B: Webhook 回调

完整契约见 [05.business-callback-guide.md](05.business-callback-guide.md),对接步骤概要:

1. 流程管理员在「业务回调」页新建订阅: 填接收 URL、选择事件类型(`taskCreated`/`taskCompleted`/`instanceFinished`)、生成签名密钥;
2. 接收方按 §5 验签(`X-Forge-Timestamp` + `X-Forge-Signature`,HMAC-SHA256,5 分钟窗口防重放);
3. 载荷契约见 05 §6 —— `instanceFinished` 事件带 `businessKey` 与终态,据此回写业务状态;
4. 投递失败自动重试(0/2/10s),接收方返回 2xx 即成功;**必须实现幂等**(同一 eventId 可能重发),管理端可查投递记录并手动重发。

### 6.3 形态 A 的补充: 触发器节点

若业务需要"流程走到 X 节点时执行 Y 动作"(而非仅状态回写),在模型里给该位置插入触发器节点,写一个 `@FlowLongTrigger` Bean 承接,四种模式(bean/expression/class/delegateExpression)与失败行为见 [03.trigger-bean-guide.md](03.trigger-bean-guide.md)。触发器与流程同事务,适合强一致动作;弱一致通知走 §6.1/§6.2。

## 7. 业务侧联动操作

发起与回写之间的过程操作,均已有现成接口(A 形态注入对应 Service,B 形态调 HTTP,路径一致):

| 动作 | 接口 | 说明 |
|---|---|---|
| 按单据查流程 | `GET /workflow/instance/by-business-key?businessKey=` | 业务详情页"查看审批进度"入口 |
| 流程图 | `GET /workflow/instance/{id}/diagram` | 返回 SVG,含高亮轨迹 |
| 审批意见 | `GET /workflow/instance/{id}/comments` | 时间线展示 |
| 流程变量 | `GET /workflow/instance/{id}/variables` | 排查分支走向问题 |
| 催办 | `POST /workflow/instance/{id}/urge` | 提醒当前待办人(站内信/邮件) |
| 发起人撤销 | `DELETE /workflow/instance/{id}` | 单据作废/撤回场景,引擎走 terminate,触发 **rejectComplete**(instanceState=5) 而非 revokeComplete 事件,回写侧须按 state 细分 |
| 唤醒(重审恢复) | `POST /workflow/instance/{id}/resume` | 挂起/驳回停滞实例的恢复,见 [01.workflow-usage.md](01.workflow-usage.md) |

审批人侧操作(待办/已办/认领/审批/驳回/转办/委派/加签/减签/拿回/撤回)全部在 `/workflow/task/*`,业务前端一般直接复用平台「待办任务」页面,无需重复开发;业务页面只做"发起 + 进度展示 + 状态联动"三件事即可。

## 8. 安全与租户注意

- **创建者构建必须走 `FlowCreatorFactory`**(user/system/restore 三个入口),它负责把 `TenantContextHolder` 的租户 ID 传导到 FlowLong 实体,直接 `new FlowCreator()` 会导致 flw_ 表 `tenant_id` 落 NULL,多租户模式下数据不可见。
- `@Async` 事件消费线程**不继承**请求线程的租户上下文,Handler 里若调平台带租户隔离的查询,需自行 `TenantContextHolder.setTenantId(...)`(从事件实体里取)并在 finally 清理。
- 发起范围由流程定义的发起范围配置控制(0 全员 / 1 指定人员 / 2 均不可发起,工作流管理员豁免),业务侧对接测试时若遇 403 类提示先查这里。
- HTTP 形态的令牌即平台登录用户,发起人身份 = 令牌对应用户;不要用管理员令牌代发,否则审批记录、发起人自选、撤回权限都会错位。

## 10. FAQ

**Q1: 发起接口拿不到 instanceId,业务表怎么回写?**
`start` 设计为 void。发起后按 businessKey 查回(`getInstancesByBusinessKey` / `GET by-business-key`),取在途实例(`endTime == null`)的 id 回写。这也是 §4 强调 businessKey 规范的原因。

**Q2: 定时任务/异步线程里能发起流程吗?**
不能直接调 `startProcess`(无用户上下文会 401)。三个替代: ① 前端触发而非后台触发; ② 用发起人身份走 HTTP; ③ 系统级无人流程考虑触发器/子流程建模规避。

**Q3: Spring 事件、Webhook 回调、触发器,三者怎么选?**
回写业务状态 → 平台内用 Spring 事件(§6.1),外部系统用回调(§6.2);特定节点执行业务动作 → 触发器(§6.3)。三者不互斥,一个业务常见组合是"触发器做强一致动作 + 事件做状态回写"。

**Q4: 同一单据被发起两次怎么办?**
引擎不限制 businessKey 重复。业务侧负责防重: 发起前查在途实例(见 §5.1 示例),或给业务表加唯一约束(单据 ID + 状态=审批中)。

**Q5: 事件里能拿到流程变量吗?**
任务事件可从 `nodeModel` 取节点配置;实例变量用 `instanceService.getProcessVariables(instanceId)` 反查。回调载荷的字段清单见 [05.business-callback-guide.md §6](05.business-callback-guide.md)。

**Q6: 业务模块能直接操作引擎(FlowLongEngine)吗?**
不建议。统一走 `Wf*Service` 门面,它们封装了身份构建、租户传导、发起范围校验、事件发布。绕过门面直调引擎的行为不受上述约束保护。
