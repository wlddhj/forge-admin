# 审批流程模块使用说明

> 适用版本: forge-admin (基于 FlowLong 1.2.7,flowlong-spring-boot-starter Boot3 兼容排除传递依赖)
> 适用对象: 流程管理员、审批配置人员、最终用户

---

## 1. 模块概览

forge-admin 工作流模块基于国产开源引擎 **FlowLong**,提供完整的流程设计、部署、发起、审批、跟踪能力。

核心能力:

- **可视化建模**: 浏览器内钉钉式卡片设计器(开始/审批/抄送/条件分支/条件审批/触发器/并行分支/包容分支/子流程/定时器/自动通过拒绝/路由分支)
- **灵活审批人**: 指定用户、角色、部门、岗位、发起人、连续多级部门负责人、表达式等 11 种策略
- **多种办理方式**: 或签/会签/依次审批/票签(权重+门槛),加签(前/后/并行)与减签
- **流程控制**: 条件/包容/路由三类网关,驳回策略(回发起人/上一节点/指定节点/终止),任务退回、撤回、拿回、催办、实例唤醒
- **AI 智能**: AI 审批(节点通过/驳回决策,异步) + AI 路由(网关分支决策,同步限时),详见 §8 与 [04.ai-approval-and-routing.md](04.ai-approval-and-routing.md)
- **完整追溯**: 实例轨迹、审批意见时间线、任务历史、抄送、AI 决策审计

## 3. 核心概念

理解下面四个概念的层级关系,有助于掌握整个模块:

```
模型 (wf_process_ext,process_id 为空=草稿)    画出来的流程图,未发布
   │  部署
   ▼
流程定义 (wf_process_ext / flw_process) 可发起的流程,版本化
   │  发起
   ▼
流程实例 (flw_instance / flw_his_instance) 一次具体的审批
   │  流转
   ▼
任务 (flw_task / flw_his_task)          每个审批节点上具体要处理的事
```

- **模型**: 在「模型管理」中画图、保存,但**还不能发起**。
- **流程定义**: 模型部署后产生,标记为「激活」状态后可以发起。
- **流程实例**: 用户点「发起」后生成一个实例,沿流程图流转。
- **任务**: 每个审批节点上生成一个待办,分配给候选人处理。

## 4. 完整配置流程(管理员视角)

从零开始接入一个审批业务的标准步骤:

### 4.1 创建流程分类(可选但建议)

路径: **流程管理 → 流程分类**(树表展示)

| 字段 | 必填 | 说明 |
|---|---|---|
| 分类名称 | ✓ | 显示名,如「人事类」「财务类」 |
| 父分类 |  | 树形选择,顶级不选;不能选自身或其子分类(防环校验) |
| 状态 | ✓ | 启用/禁用 |

> **分类编码自动生成**: 系统按层级码自动生成——父分类编码 + 每级 2 位随机段(数字+大写字母,同级去重),不支持手工修改。移动分类到新父级时,自身重新生成段,子孙编码做**前缀级联替换**,模型/流程按编码关联的引用不受影响。

> **筛选联动**: 「模型管理」「审批流程」页左侧分类树,点击节点按编码前缀命中整个子树过滤列表(分类管理页的「分类编码」查询框同样支持前缀模糊)。

### 4.2 创建/编辑表单(可选)

路径: **流程管理 → 表单管理**

支持两种类型:

- **流程表单**: 表单与流程绑定,仅在该流程中可用
- **业务表单**: 业务系统提供的 URL,审批时跳转业务页面

点击「设计」按钮进入表单设计器,拖拽字段、配置校验规则。表单 JSON 会保存到 `wf_form.conf` / `wf_form.fields`。

### 4.3 设计流程模型

路径: **流程管理 → 模型管理 → 设计**

进入 FlowLong 钉钉式可视化设计器:节点自上而下卡片排列,鼠标悬停节点间的「+」号弹出节点菜单(12 类),点节点卡片打开右侧抽屉配置属性。

**可添加的节点类型**:

| 节点 | type | 用途 |
|---|---|---|
| 审批节点 | 1 | 人工审批(或签/会签/依次/票签) |
| 抄送节点 | 2 | 知会,不产生待办 |
| 条件分支 | 4 | 排他网关,条件命中选一条走(§6) |
| 条件审批 | 3 | 条件分支内的"条件+审批人"组合 |
| 触发器任务 | 7 | 自动执行逻辑后流转(§7) |
| 并行分支 | 8 | 所有分支同时执行,全完成才汇聚 |
| 包容分支 | 9 | 条件命中的分支全部执行(可多条) |
| 子流程 | 5 | 调起另一个流程,结束回父流程 |
| 定时器 | 6 | 等待 `"2:h"` 时长或 `"HH:mm:ss"` 时刻 |
| 自动通过 / 自动拒绝 | 30/31 | 仅分支内使用,无后续节点 |
| 路由分支 | 23 | 按条件**直接跳转**到指定节点(可回跳) |

**审批节点关键配置**:

| 配置项 | 说明 |
|---|---|
| 节点名称 | 显示在审批人待办列表中的标题 |
| 候选人策略 | 见第 5 节,决定谁能审批 |
| 多人审批方式 | examineMode:或签/会签/依次/票签(权重+passWeight 门槛) |
| 驳回策略 | 默认终止 / 回发起人 / 上一节点 / 指定节点 + 重审策略;未配置保持存量终止行为 |
| 超时提醒 | `remindAuto=true` + `remindAdvanceMinutes=N`,支持 websocket/邮件渠道 |
| AI 审批 | 见第 8 节 |

**分支网关额外能力**:条件/包容/路由网关顶部的「AI 路由」按钮可启用 AI 分支决策(见第 8 节)。

保存后模型 JSON 记录在 `wf_process_ext.model_json`（process_id 为空即草稿），部署时引擎规范化写入 `flw_process.model_content`。

### 4.4 部署流程

模型设计完成后,点击工具栏的「部署」按钮(或在「模型管理」列表中点「部署」):

- 系统会创建一条 `flw_process` 记录,生成 `processId`
- 在 `wf_process_ext` 中记录流程扩展信息
- 部署后流程进入「激活」状态,出现在「审批流程」列表

> **多次部署**: 同一模型可以多次部署,FlowLong 自动按版本号管理,旧版本标记为「历史版本」。

> **发起校验**: 发起时后端会校验模型(节点 KEY 唯一、审批人已配、子流程已选、AI 路由网关必须有默认分支等),不合法直接 400 提示。

### 4.5 发起流程

路径: **流程管理 → 流程实例 → 发起** 或在「审批流程」列表中点「发起」

- 选择要发起的流程(受 use_scope 发起范围控制:全员/指定人员/均不可,管理员豁免)
- 填写业务表单(自定义表单会内嵌,业务表单会跳转)
- 提交后生成 `flw_instance` 活动实例,沿流程图自动流转到第一个审批节点

## 5. 候选人策略

审批节点上设置「谁能审批」时,有以下策略可选:

| 策略 | 编码 | 适用场景 | 参数说明 |
|---|---|---|---|
| 指定角色 | 10 | 同一类角色的人都能审 | 角色 ID |
| 部门成员 | 20 | 整个部门的人都能审 | 部门 ID |
| 部门负责人 | 21 | 部门 leader 审批 | 部门 ID |
| 指定岗位 | 22 | 同一岗位都能审 | 岗位 ID |
| 指定用户 | 30 | 直接指定若干人 | 用户 ID 列表 |
| 审批人自选 | 34 | 当前审批人临时选下一个审批人 | 无 |
| 发起人自选 | 35 | 发起时让发起人选 | 无 |
| 发起人自己 | 36 | 让发起人自己审批(常见于复核) | 无 |
| 发起人部门负责人 | 37 | 发起人所在部门的 leader | 无 |
| 连续多级部门负责人 | 38 | 一级 → 二级 → 三级 leader 链式审批 | 级数 |
| 表达式 | 60 | 用 SpEL 表达式动态计算 | 表达式 ID(见下) |

### 5.1 表达式策略详解

候选人为「表达式」时,审批人通过 `wf_process_expression` 表的 ID 引用,运行时 `ExpressionCandidateStrategy` 会查表并计算。

支持的内置变量:

```
${initiator}              流程发起人
${startUser}              同上(别名)
${startUserDeptLeader}    发起人部门负责人(查 sys_dept.leader)
${form_xxx}               表单字段 xxx 的值(取的是用户 ID)
${流程变量名}             直接读流程变量,支持单值/逗号分隔/集合
```

**使用步骤**:

1. 「流程管理 → 表达式管理」新增一条表达式,`expression` 字段填以上语法
2. 设计流程时,节点的 `candidateStrategy=60`,`candidateParam` 填这条表达式的 **ID**(数字)
3. 运行时引擎自动查表并计算候选人

## 6. 分支节点与条件路由

四类分支容器的语义差异:

| 分支 | type | 走法 | 典型用途 |
|---|---|---|---|
| 条件分支 | 4 | 条件命中**选一条**走(排他) | 按金额/等级走不同审批链 |
| 包容分支 | 9 | 条件命中的**多条同时**走 | 多条件并行审查 |
| 并行分支 | 8 | **全部**同时走,无条件的"且" | 固定并行会签 |
| 路由分支 | 23 | 按条件**直接跳转**到指定节点 | 打回重审循环/跨区域跳转 |

**关键澄清**: 条件路由的正确做法是 **type=4 + 多个 type=3 子节点**(每个子节点代表一个"条件+审批人"组合);单独拖出的 type=3 条件审批节点 conditionList 不生效(行为同普通审批)。完整细节见 [02.condition-node-guide.md](02.condition-node-guide.md)。

**默认分支兜底**: 每个条件/包容/路由网关都应保留一条**无条件分支**(conditionList 为空)作为"以上都不匹配"的兜底——启用 AI 路由的网关**强制要求**有默认分支,发起时校验。

典型组合: **触发器节点写变量 → 条件分支读变量路由**(§7 / [02.condition-node-guide.md §8](02.condition-node-guide.md#8-完整示例触发器--条件分支组合))。

## 7. 触发器任务(独立节点)

触发器节点(type=7)是**独立的流程节点**,在 FlowLong 模型中作为一个节点存在。引擎到达该节点时,根据 `extendConfig.triggerType` 字段,自动执行一段逻辑后**直接跳到 childNode**,不需要人工审批。

### 7.1 4 种业务模式

| 模式 | 配置字段 | 适用场景 | 推荐度 |
|---|---|---|---|
| `expression` | `triggerExpression` SpEL | 简单条件判断 / 写流程变量 | ★★★ 80% 场景 |
| `bean` | `triggerBean` + `triggerMethod` | 复杂业务逻辑(调 Spring Bean) | ★★★★★ 90% 复杂场景 |
| `class` | `triggerClass` FQCN + `triggerMethod` | 第三方 jar 工具类 | ★★ 特殊场景 |
| `delegateExpression` | `triggerExpression` SpEL(求 Bean 名) + `triggerMethod` | 按 ctx 动态选 Bean | ★★★ 多租户/多业务线 |

### 7.2 模式选择速查

```
需要"写变量"或"简单条件判断"?
  ├─ 是 → expression 模式
  └─ 否 → 复杂业务逻辑?
            ├─ Spring 容器里的 Bean → bean 模式
            ├─ 第三方 jar / 工具类 → class 模式
            └─ 按 ctx 动态选 → delegateExpression 模式
```

### 7.3 expression 模式 — SpEL 表达式

**extendConfig 配置**:
```json
{
  "triggerType": "expression",
  "triggerExpression": "${amount > 1000000 ? T(SpelUtil).setVar(execution, 'riskLevel', 'A') : false}"
}
```

**设计器配置步骤**:
1. 在触发器节点抽屉,业务模式选 `expression - SpEL 表达式`
2. 填入 SpEL 文本

**常用 SpEL 例子**:

```spel
# 简单条件
${amount > 1000}

# 写流程变量
${T(SpelUtil).setVar(execution, 'riskLevel', amount >= 1000000 ? 'A' : 'B')}

# 调 Spring Bean
${@auditService.logEvent('contract_signed', execution.getFlwInstance().getId())}
```

### 7.4 bean 模式 — 调 Spring Bean(推荐)

**extendConfig 配置**:
```json
{
  "triggerType": "bean",
  "triggerBean": "contractRiskTrigger",
  "triggerMethod": "execute"
}
```

**前置条件**:
- Bean 必须带 `@Component` 和 `@FlowLongTrigger` 注解
- 推荐继承 `AbstractFlowLongTrigger` 抽象基类

**设计器配置步骤**:
1. 业务模式选 `bean - Spring Bean(白名单)`
2. 从下拉选 Bean(后端 `GET /workflow/trigger/beans` 拉取)
3. 填方法名(默认 `execute`)

**示例 Bean**:

```java
@Component
@FlowLongTrigger(name = "合同风险评估", description = "根据金额分级")
public class ContractRiskTrigger extends AbstractFlowLongTrigger {
    @Override
    public boolean execute(Execution execution, NodeModel nodeModel, Map<String, Object> ctx) {
        Long amount = requireArgAs(ctx, "amount", Long.class);
        String riskLevel = amount >= 1_000_000 ? "A" : amount >= 100_000 ? "B" : "C";
        setVar(execution, "riskLevel", riskLevel);
        return true;
    }
}
```

**完整开发指南**: [03.trigger-bean-guide.md](03.trigger-bean-guide.md)

### 7.5 class 模式 — 反射 Java 类

**extendConfig 配置**:
```json
{
  "triggerType": "class",
  "triggerClass": "com.example.LegacyAuditor",
  "triggerMethod": "execute"
}
```

完全脱离 Spring 容器,`@Autowired` 字段为 null。生产建议加包前缀白名单。

### 7.6 delegateExpression 模式 — SpEL 求 Bean 名

**extendConfig 配置**:
```json
{
  "triggerType": "delegateExpression",
  "triggerExpression": "industry == 'tech' ? 'techContractRiskTrigger' : 'financeContractRiskTrigger'",
  "triggerMethod": "execute"
}
```

SpEL 求值结果必须是带 `@FlowLongTrigger` 注解的 Bean 名。典型场景:多租户按 tenantId 选 Bean。

### 7.7 失败行为

- `return true` → 流程正常流转到 childNode
- `return false` 或 `throw Exception` → 流程**不流转**,异常向上冒泡
- 节点配置 `continueOnError=true` → 忽略失败,继续流转

详见 [03.trigger-bean-guide.md §8](03.trigger-bean-guide.md#8-返回值约定与异常处理)。

### 7.8 适用场景

- **业务数据预处理**: 提交后自动写库(写风险等级、计算金额)
- **流程分支前置判断**: 根据表单数据设置流程变量,供下游条件分支读
- **自动通知/抄送**: 关键节点自动给干系人发消息
- **业务归档**: 流程结束后自动归档历史数据
- **跨系统数据同步**: 流程走到某步时自动调外部 API

> **不要**把复杂业务(调 API、写业务表)全堆在触发器节点,触发器最适合"轻量级旁路判断"。

## 8. AI 智能审批与 AI 智能路由

两个能力一句话:**AI 审批**在审批节点上决定"这条任务过不过";**AI 路由**在分支网关上决定"流程走哪条"。二者互补可组合。

### 8.1 AI 智能审批(审批节点)

- 设计器: 审批节点抽屉打开「AI 审批」开关,配置模型/置信度阈值/回退策略(转人工/默认通过/默认驳回)/提示词/超时
- 机制: 任务创建后**异步**执行(事务提交后 workflowExecutor 线程),高置信度自动通过/驳回并写审批意见,低置信度或失败按回退策略处理;已被人工办理的任务自动放弃(幂等)
- 审计: `wf_ai_approval_record`(决策/置信度/理由/原始响应)

### 8.2 AI 智能路由(分支网关)

- 设计器: 条件/包容/路由网关顶部「AI 路由」按钮,配置路由提示词/模型/超时(默认 30s)/置信度阈值
- 机制: 流程到达网关时**同步**由 AI 根据流程变量+候选分支清单选分支;AI 失败/超时/低置信度/返回无效分支时,自动落回 SpEL 条件判断 → 默认分支,全程不卡流程
- 强制规则: 启用 AI 路由的网关必须保留无条件默认分支(发起校验 400 拦截)
- 审计: `wf_ai_route_record`(候选/命中分支/置信度/理由/原始响应/状态)

配置细节、降级状态机、排查 SQL 与注意事项见 **[04.ai-approval-and-routing.md](04.ai-approval-and-routing.md)**。

## 9. 待办与已办

### 9.1 待办任务

路径: **流程管理 → 待办任务**(可切换「我的待办 / 抢办池」视图)

显示当前用户作为候选人的所有待办,操作:

| 操作 | 说明 | 触发 |
|---|---|---|
| 审批 | 同意流转到下一节点 | 任务完成 |
| 驳回 | 按节点驳回策略回到发起人/上一节点/指定节点 | 任务驳回 |
| 委派 | 临时让其他人处理,处理完回到你 | 委派 |
| 转办 | 永久转给其他人,你不再参与 | 转办 |
| 认领 / 取消认领 | 多个候选人时抢办;认领后可反悔放回 | 认领 |
| 加签 / 减签 | 前加签/后加签/并行加签;减签按参与人移除 | 加签 |
| 催办 | 提醒当前受理人(实例级 30 分钟节流) | 催办 |
| 退回 | 退回到之前任一节点 | 退回 |
| 撤回 | 发起人在审批人操作前撤回整个流程 | 撤回 |

### 9.2 已办任务

## 13. 常见问题

### Q1: 模型已部署但「审批流程」列表找不到?

A: 检查「状态」筛选是否只勾选「激活」。已部署但未激活的流程只在「模型管理」中可见。

### Q2: 候选人策略选了「部门负责人」但任务没人接?

A: 检查 `sys_dept.leader` 字段是否填写且对应用户名在 `sys_user` 中存在。

### Q3: 表达式策略怎么写?

A: 在「表达式管理」中新增,表达式内容用 `${initiator}` / `${form_xxx}` 等语法,然后节点的 `candidateParam` 填这条表达式的 ID(**不是名称**)。

### Q4: 表单字段值怎么传到候选人?

A: 用 `${form_xxx}`,其中 `xxx` 是表单字段名,值必须是用户 ID(或用户名,系统会自动转换)。

### Q5: 如何让节点超时前自动提醒?

A: 审批节点 `extendConfig` 中设置 `remindAuto=true`、`remindAdvanceMinutes=N`(可选 `remindChannels` 含 `email` 时发邮件,收件人取用户真实邮箱)。需要"到点自动办理"则用超时自动审批(`termAuto` + `termMode` 自动通过/拒绝)。

### Q6: 流程发起后能改流程图吗?

A: 已经在流转的实例**不会受新版本影响**;同一模型可重新部署,新版本只对**新发起的实例**生效。

### Q7: 怎么撤回已发起的流程?

A: 在「待办任务」或「流程实例」详情中,如果是发起人,操作栏有「撤回」按钮(仅在第一个审批人未操作前有效)。

### Q8: 拖出 type=3 条件审批节点,配置的 conditionList 不生效?

A: 这是**正常行为**。type=3 单独使用时,`TaskServiceImpl` 的处理逻辑与 type=1 approval **完全相同**(直接生成 task,不读 conditionList)。要实现条件路由,正确做法是拖出 **type=4 条件分支 + 多个 type=3 子节点**,每个子节点的 conditionList 才会被引擎读取。详见 [02.condition-node-guide.md §2.2](02.condition-node-guide.md#22-作为独立节点--条件不生效)。

### Q9: 启用了 AI 路由但流程走的还是条件分支?

A: 属于降级生效——AI 未被采纳(失败/超时/低置信度/返回无效分支)会自动落回条件判断。查 `wf_ai_route_record.status` 与 reasoning 定位,详见 [04.ai-approval-and-routing.md §5](04.ai-approval-and-routing.md#5-常见问题)。
